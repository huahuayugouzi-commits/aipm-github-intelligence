# 成本优化说明

## 1. 成本原则

产品把“数据采集、排名计算、页面访问”与“AI 深度分析”分离。GitHub API 和本地程序处理确定性工作，模型只分析有价值且发生变化的项目。

## 2. 已实现机制

| 机制 | 做法 | 节省点 |
| --- | --- | --- |
| 项目去重 | 以 GitHub ID Upsert | 避免重复存储与分析 |
| 内容指纹 | README 哈希 + 核心产品字段 + 变化区间 | 无重要变化时复用分析 |
| 持久化缓存 | 分析结果写入 SQLite | 多用户/多次刷新读取同一结果 |
| 只读页面 | 页面不调用 GitHub 或 AI API | 访问量不放大模型成本 |
| 分层任务 | 每日只采集计数；每周才执行完整流程 | 降低 README 与 AI 调用频率 |
| 数量限制 | 每次最多分析可配置数量 | 控制最坏成本 |
| 输入/输出限制 | README 字符和模型输出 Token 上限 | 降低单次成本 |
| 多级预算 | 日/周/单次 Token，日/周费用 | 防止异常消耗 |
| 版本化缓存 | 模型 + Prompt 版本 + Schema 版本 | 平衡复用与结果正确性 |
| 调用审计 | 模型、Token、费用、缓存、时间、成功率 | 支持成本复盘 |

## 3. 费用计算

模型单价通过 `AI_INPUT_PRICE` 和 `AI_OUTPUT_PRICE` 配置，单位为每 100 万 Token。单次估算费用：

```text
input_tokens / 1,000,000 × input_price
+ output_tokens / 1,000,000 × output_price
```

价格为 0 时只记录 Token，不假设厂商价格。费用上限为 0 可用于关闭对应费用闸门，Token 预算仍然生效。

## 4. 缓存失效策略

以下变化可能触发重新分析：README、描述、License、Homepage、分类、Star 或 Fork 跨越设定变化区间。Prompt 或 Schema 版本变化也会自然生成新的缓存命名空间。

该策略避免“任何一个 Star 变化就重跑”，同时能捕捉产品定位、许可和成熟度的显著变化。

## 5. 监控指标

- 本周真实模型调用次数；
- 输入/输出 Token；
- 估算费用；
- 缓存命中率；
- AI 分析成功率；
- 降级原因与最近错误；
- 单次任务采集/分析/失败数量。

Mock 与来源未知的历史记录不计入真实模型预算，避免演示数据污染成本看板。

## 6. 下一步优化

- 把 README 先由程序提取产品、部署、License 等证据段，再送入模型。
- 对低 AIPM 分项目完全跳过 AI 分析。
- 按业务价值动态分配输出 Token，而不是统一上限。
- 增加月度预算、预算预警与单位有效分析成本。
