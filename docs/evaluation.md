# 评测与可靠性

## 1. 评测目标

本项目同时评估三类质量：数据是否真实可追溯、AI 输出是否结构稳定、故障时主体产品是否仍可用。当前自动化测试使用 Vitest 和隔离的 SQLite 测试库。

## 2. 核心验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| GitHub 请求失败 | 记录失败；已有项目仍可生成部分周报 |
| GitHub Rate Limit | 任务安全失败，不破坏数据库 |
| 首次运行 | 七日/三十日增长榜显示“历史数据积累中” |
| 重复采集 | 按 `github_id` Upsert，不生成重复项目 |
| README 与核心数据未变化 | 复用 AI 缓存，模型不重复调用 |
| AI JSON 不符合 Schema | 拒绝写入非法分析并记录失败 Token |
| AI 服务不可用 | GitHub 数据与周报照常保存，进入降级模式 |
| Token/费用预算不足 | 停止新分析，保留采集与报告 |
| 定时任务重复触发 | 数据库锁拒绝第二次执行 |
| 部分仓库采集失败 | 生成部分成功报告并明确失败项 |
| 页面连续读取 20 次 | AI 调用数不增加 |
| 10 个并发周报读取 | 读取同一份持久化内容 |
| 缺少 AI Key | 排行榜与历史数据仍可读 |
| 本周热门 | 只按真实七日快照增量，不回退累计 Star |
| 每日快照 | 只更新计数，不调用 AI、不生成周报 |

## 4. AI 分析人工评测建议

建立 20–30 个项目的小型 Golden Set，由产品经理依据 README 标注：

- 事实忠实度：`verifiedFacts` 能否在仓库证据中找到；
- 边界清晰度：推测是否进入 `assumptions`；
- 产品可操作性：是否能支持复刻、竞品或面试表达；
- 一致性：相同输入多次输出的结构与关键结论是否稳定；
- 成本效率：单项目 Token 与可用信息密度。

建议采用 1–5 分量表，并记录 Bad Case、证据链接、问题类型、修复版本和回归结果。
